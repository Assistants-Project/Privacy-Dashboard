# Requirements Gap Analysis (Dashboard vs RequirementsDocument.md)

Date: 2026-02-27

This file lists the main mismatches (Missing / Partial / Different) between the requirements in `docs/RequirementsDocument.md` and the current implementation (backend + frontend). It also lists a few notable extra behaviors not explicitly mentioned in the requirements.

Legend:
- Missing: not implemented
- Partial: implemented but incomplete
- Different: implemented with a different flow/semantics than specified
- Extra: implemented but not specified in requirements

## Functional Requirements / Use Case Gaps

| Req ID | Requirement (short) | Gap | Current behavior in dashboard | Evidence (code / endpoints) | Notes |
|---|---|---|---|---|---|
| FR1.1 / UC1 | Registration asks username + email + password + role | Different / Partial | Registration is email-based (no username). Data Subject registration requires Smartotum credentials | `backend/app/models/entities/user.py` (no username), `frontend/src/components/Authentication/Registration.tsx`, `backend/app/services/auth_service.py` | UC1 scenarios assume local username/password registration; current design delegates DS identity to Smartotum |
| UC1.4 | Only 1 DPO can exist | Missing | Multiple DPO accounts can be created | `backend/app/repositories/user_repository.py` (no uniqueness), `backend/app/services/auth_service.py` | Requirements explicitly include “DPO already exists” failure scenario |
| FR1.3 / UC3 | Manage account: change email/password | Missing | No UI/API for updating profile/email/password (only delete current) | `backend/app/controllers/user_controller.py` (no update routes), `backend/app/controllers/auth_controller.py` (`/current` delete only), frontend routes in `frontend/src/pages/PrivacyDashboard.tsx` | Biggest “account” gap |
| UC2.4 | Login fails if user already logged in | Different | Backend login does not enforce “unlogged only”; UI redirects if already authenticated | `backend/app/controllers/auth_controller.py` (`unlogged_required` commented), `frontend/src/pages/Authentication/Login.tsx` | Minor mismatch (mostly UX) |
| UC2.5 | After DS selects home, system automatically syncs apps from SIFIS-Home | Partial / Different | Sync is user-driven via refresh endpoints (not strictly automatic at login/home select) | `backend/app/controllers/home_controller.py` (`POST /api/homes/refresh`), `backend/app/controllers/application_controller.py` (`POST /api/applications/refresh`) | Requirements describe an automatic sync step; current product exposes explicit sync actions |
| FR2.2 | Contact details include role + related apps | Partial / Missing | UI shows name/email; API returns user fields but no “apps related to contact” view | `backend/app/controllers/user_controller.py` (`/contacts`), `backend/app/schemas/response/user_res_schema.py`, `frontend/src/pages/Messages/Messages.tsx` | Role exists in DB/API but is not shown in the chat UI; apps-by-contact not exposed |
| FR2.1.1 | DC/DPO contacts are users they have interacted with + can send updates/notices | Different / Partial | Contacts are computed by “common applications”, not strictly by past interactions; updates/notices are just normal messages | `backend/app/services/user_service.py` (`get_contacts_by_user_id`), `backend/app/repositories/user_repository.py` (`get_contacts_by_user_id`) | If “interacted” must be strict, contacts should be derived from message/request history |
| FR3.3 | Search contacts by name/email/role among messaged contacts | Partial | Search exists only in “new chat” modal and filters by name/email, not by role | `frontend/src/components/Messages/ContactsModal.tsx` | “Role” filtering/search is not implemented |
| FR3.5 / UC5 | Message attachments (send + download) | Missing / Partial | Frontend has no attachment UI; backend only stores an optional string path (no upload/download) | `backend/app/schemas/request/message_req_schema.py`, `backend/app/services/message_service.py`, `frontend/src/pages/Messages/Messages.tsx` | UC5 expects notifications + download prompt for attachments; not implemented |
| FR4.6 | DS can exercise all GDPR rights (access, withdrawal, portability, erasure, limitation, complaint) | Partial | Rights list is incomplete (no portability, no limitation) | `frontend/src/models/request.ts` (`RightType` enum) | If required, add missing right types + backend support |
| FR4.2 | Request details include DS name + right + status, etc | Partial | Requests expose DS email + request fields; no DS name in request payload | `backend/app/schemas/response/request_res_schema.py`, `backend/app/repositories/request_repository.py` | UI can still show email, but requirement explicitly mentions DS name |
| FR4.9 / UC6.1 step 7 | Reconfigure IoT device when request becomes HANDLED | Different | Consent-related reconfiguration happens at request submission (withdraw) and at consent acceptance, not on “handled” | `backend/app/services/request_service.py` (withdraw flow creates DHT rules), `backend/app/services/request_service.py` (`handle_request` only updates DB status) | Requirement ties enforcement to “handled”; current approach is “immediate enforcement” |
| FR5.2 / UC8 | DC/DPO app details include list of bound Data Subjects | Missing | Managed app details do not include DS list | `backend/app/schemas/response/application_res_schema.py`, `frontend/src/models/app.ts`, `frontend/src/components/Apps/AppDetailsPanel.tsx` | UC8 requires selecting a DS from an app and opening DS details |
| FR5.3 | DC/DPO can access DS personal info + communication history + requests from app context | Missing | No “per-app per-user” drill-down view; messages/requests exist but not linked as in UC8 | Frontend routes in `frontend/src/pages/PrivacyDashboard.tsx`, absence of related components | Would require new UI + endpoints aggregating user/app data |
| FR5.5 | DS app details include list of high-level policies defined | Partial / Different | Policies exist in Policy Translation page, but app details panel does not show them; policies are not scoped to an app | `frontend/src/pages/PolicyTranslation/PolicyTranslation.tsx`, `frontend/src/components/Apps/AppDetailsPanel.tsx` | Requirements phrase policies “for a specific application”; current model is home/device-oriented |
| FR5.6 / UC9.2 | DS downloads (1) Privacy Notice and (2) consents document as XML and JSON | Partial / Missing | Privacy Notice can be downloaded (PDF), but no consents “document” export (XML/JSON) exists | `frontend/src/components/PrivacyNotice/PrivacyNoticeEditor.tsx`, `backend/app/controllers/consent_controller.py` (state only) | Only consent state listing is implemented; export endpoints/formats missing |
| FR5.9 / FR5.10 | Withdraw consent(s) is a “request” (not immediate), including withdraw-all UX | Different / Partial | UI submits a right request, but backend also revokes consents and applies deny rules immediately; withdraw-all is “Select all” not a dedicated single action | `frontend/src/components/Rights/SubmitRightRequestModal.tsx`, `backend/app/services/request_service.py` (withdraw flow), `backend/app/services/consent_service.py` (accept flow) | Requirements describe request + handled flow; current product enforces immediately for withdraw consent |
| FR5.11 / UC9.1 | “Request removal of all personal data” is a dedicated action | Partial | Implemented via generic “Exercise Rights” modal (right types), not a dedicated button/flow in app details | `frontend/src/components/Apps/AppDetailsPanel.tsx`, `frontend/src/components/Rights/SubmitRightRequestModal.tsx` | May be acceptable UX, but it diverges from UC9.1 step 3 |
| FR5.9.1 / FR5.10.1 / FR5.11.1 | “Generate automatic message to relevant data controllers” for withdraw/erase | Missing / Different | Requests are stored in DB; no automatic “message to controllers” is generated | `backend/app/repositories/request_repository.py` (create_request only), `backend/app/services/request_service.py` | If “message” must be a real chat message, add MessageRepository.create_message on request submission |
| FR5.12 / FR5.13 | Automatic app add/remove on DS install/uninstall | Partial | Sync exists, but it is triggered via refresh/integration calls (not truly automatic) | `backend/app/services/smartotum_service.py`, `backend/app/controllers/application_controller.py` (`/refresh`) | May be acceptable in demo; strict “automatic” would require webhook/event integration |
| FR5.15 | Reconfigure IoT device to align with updated privacy consent | Partial / Different | Reconfiguration exists for consent withdraw/accept (and default-deny), but not clearly tied to “handled request” and not implemented for all right types | `backend/app/services/request_service.py`, `backend/app/services/smartotum_service.py` | Scope depends on which rights should translate into device reconfiguration |
| FR9 / UC5-UC7 | Notifications for messages/requests/PN/PIA/questionnaire | Missing | Notification models exist, but no notification API/UI is present | `backend/app/models/entities/notification.py` (model only), no notification controller in `backend/app/controllers` | UC5/UC6/UC7 explicitly rely on notifications |

## Extra Behaviors (Not Explicitly Mentioned in Requirements)

| Area | Extra behavior | Evidence | Notes |
|---|---|---|---|
| Consents | “Privacy by default”: when apps/consents are synced and a consent is not given, a deny rule may be created automatically (based on `sifis_action_id`) | `backend/app/services/smartotum_service.py` (default deny rule creation), `backend/app/services/consent_policy_rule_service.py` | Requirements describe reconfiguration on handled requests; this extends enforcement also to “not given by default” state |
| Policy Translation | Simulation endpoints for SIFIS rules | `backend/app/controllers/sifis_controller.py` (`/simulation/*`) | Not referenced in requirements document |
| DHT tooling | Dedicated DHT browsing endpoints (`get_all`, `topic_name`) | `backend/app/controllers/dht_controller.py` | Useful for debugging/demo; not in requirements |
| Debug | Debug reset/clear endpoints for homes | `backend/app/controllers/home_controller.py` (`/debug/*`) | Out of scope for production requirements |
